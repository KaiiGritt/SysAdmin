// 01 — About This Portfolio

Purpose & Introduction

"Every system I broke this semester taught me more than every system that worked perfectly."

This portfolio is not just a collection of submitted outputs — it is a documented record of genuine learning. From the moment I pressed F2 on Lab Desktop #4 and entered the BIOS for the first time, to the moment two virtual machines successfully exchanged files across a network that existed entirely in software, this semester was a series of small breakthroughs built on larger misunderstandings.

The work compiled here spans two arcs: Progress Assessments, where I explored the conceptual foundations of networking, virtualization, and system security — and Laboratory Activities, where those concepts became real, tactile, and occasionally frustrating in the best possible way.

Each module entry follows a deliberate structure: the challenge I faced, the approach I took, and the outcome I arrived at — along with what actually stayed with me. Because in IT, understanding why something works matters just as much as knowing how to make it work.

Progress Assessment · Network Protocols
Network Protocols & Services A
TCP, UDP, and the three-way handshake
ChallengeUnderstand why some network conversations need perfect reliability while others just need raw speed — and articulate when each protocol is the right tool.
ApproachStudied TCP's reliability stack: the handshake, ACKs, retransmission logic, and congestion control — then contrasted this against UDP's lightweight, fire-and-forget model.
OutcomeA clear mental model for protocol selection — knowing when integrity beats latency and vice versa.
TCP
Connection-oriented
Ordered + reliable delivery
ACK + retransmission
Flow & congestion control
Best for: web, email, file transfer
UDP
Connectionless
No delivery guarantee
Lower overhead
Faster, leaner packets
Best for: streaming, VoIP, DNS, games
💡 What Stayed With Me The three-way handshake (SYN → SYN-ACK → ACK) is a deceptively simple ritual. Every "smooth" web experience is actually the product of thousands of polite negotiations happening invisibly, every second.

Network Protocols & Services B
DNS & DHCP — the phonebook and the receptionist
ChallengeUnderstand the two background services that make networks feel "automatic" — domain name resolution and dynamic IP address assignment.
ApproachTraced a full DNS lookup journey from recursive resolver → root servers → TLD servers → authoritative server. Then walked through the DHCP discover-offer-request-acknowledge cycle and how leases work.
OutcomeA complete picture of the silent infrastructure behind every "just works" network moment — and awareness of where (and how) it can break.

Resolves domain names → IPs

DHCP

💡 What Stayed With Me The internet is mostly very fast, very polite paperwork. DNS and DHCP are that paperwork — invisible until they fail, irreplaceable once you understand them.

Progress Assessment · Virtualization
Virtualization B — Hyper-V vs. VirtualBox
Two hypervisors, two philosophies — choosing wisely
ChallengeCompare the two most widely used virtualization tools and recommend the right one for a real small-to-medium business scenario.
ApproachBroke the comparison into architecture (Type 1 vs Type 2), management tools, ecosystem integration, and feature sets — then translated that into a concrete SME recommendation.
OutcomeA decision framework for choosing hypervisors based on environment, budget, and scale — not just familiarity.
Hyper-V
  • Type 1 — bare metal
  • Enterprise performance
  • Live migration, failover
  • Best: Microsoft stack, scale
VirtualBox
  • Type 2 — runs on host OS
  • Cross-platform (Win/Mac/Linux)
  • Snapshots, cloning
  • Best: learning, mixed env.
💡 My Recommendation For a mixed-environment SME on a tight budget: VirtualBox. For Microsoft-heavy enterprise with scaling plans: Hyper-V. The tool should serve the environment — not the other way around.

Progress Assessment · System Security
System Security — Layered Defense
The healthcare provider that thought a firewall was enough
ScenarioA healthcare provider with strong SSL/TLS and a firewall — but the server sits in a shared basement behind a standard door lock, and the OS is rarely updated. Evaluate and fix it.
ApproachIdentified the two critical gaps (physical access vulnerability + unpatched OS), explained why network encryption alone fails in this threat model, and proposed a layered defense strategy.
OutcomeA working understanding that security is not a product you install — it's a practice you maintain across every layer.
⚠ KEY WEAKNESSES IDENTIFIED
1. Physical Security Gap: A shared basement with a standard lock means anyone with physical access can bypass all network-level protections entirely.

2. Unpatched OS: Known vulnerabilities in an outdated OS are documented publicly — attackers rely on administrators avoiding updates to prevent downtime.
💡 What Stayed With Me The strongest cryptography in the world means nothing if someone can walk into the basement. Security is the discipline of imagining failures before they happen — across every layer, physical and digital.

Progress Assessment · System Security
System Security A — CIA Triad & Recovery
Secure configurations and the backup that wasn't
ScenarioTwo scenarios: (1) a startup disabling logs and using default passwords for "performance"; (2) a ransomware attack that compromised both primary data and the only backup, stored on the same infected server.
ApproachApplied the CIA Triad to expose every weakness in Scenario 1. Analyzed the backup failure systematically and built a professional recovery framework for Scenario 2.
OutcomeA concrete understanding of why recovery planning is just as important as prevention — and what a real backup strategy looks like.
Confidentiality
No encryption at rest → data exposed
Integrity
No logs → no audit trail
Availability
Weak config → ransomware risk
💡 What Stayed With Me "We have a backup" is not a recovery strategy. A tested, isolated, off-site backup where the entire team knows the procedure at 2 a.m. — that's a recovery strategy.

Lab 03 · Linux Installation (3 VMs)
Installing Linux in a Virtual Machine
A second operating system, running quietly inside the first
ChallengeTake the empty VM from Lab 2 and bring it to life — install a real Linux distribution and arrive at a fully usable second operating system.
  • 1 Attach the ISO — Pointed the VM's virtual optical drive at the Linux ISO file. The equivalent of inserting a CD into a physical machine.
  • 2 Boot from media — Confirmed boot order placed the optical drive ahead of the still-empty virtual disk.
  • 3 Walk the installer — Selected language, keyboard, configured partitions (full virtual disk), set timezone, created user account and password.
  • 4 First boot — Detached the ISO so the VM wouldn't loop back into the installer. Rebooted into a live Linux desktop — same hardware, two independent worlds.
💡 What Stayed With Me The moment the Linux desktop appeared inside a VirtualBox window was genuinely surprising. Two operating systems, one machine — and it just works. Virtualization theory became very real, very fast.
🔗
Lab 04 · VM-to-VM File Sharing
VM-to-VM Configuration & File Sharing
Two virtual machines, one shared folder — networking theory becomes practice
ChallengeGet two virtual machines to discover each other on a shared network and successfully exchange files — proving Modules 5 & 6 were not just theory.
  • 1 Same network — Set both VM network adapters to Internal Network / Host-only mode, placing them on a single virtual switch where they could see each other.
  • 2 IP addressing — Confirmed each VM had an IP on the same subnet. Module 6's DHCP lesson came back here directly.
  • 3 Reachability test — Used ping from VM1 → VM2 and back. Successful replies confirmed Layer 3 connectivity.
  • 4 Enable sharing — Configured a shared folder on the source VM with appropriate read/write permissions, then accessed and transferred files from VM2.
💡 What Stayed With Me A network that exists entirely in software behaves exactly like a physical one. The same protocols, the same troubleshooting steps, the same ping command. That realization — that the virtual and physical follow identical rules — changed how I think about infrastructure.
